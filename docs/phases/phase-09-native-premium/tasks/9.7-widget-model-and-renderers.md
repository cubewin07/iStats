# Task 9.7 — Widget Model and Renderers

**Phase:** 9 (Stage C) · **Depends on:** 9.1 · **Blocks:** 9.8, 9.10 · **Rule:** 4

## Intent
Make menu bar widgets data-driven. A pure `WidgetModel` (core) turns a metric reading plus a `WidgetStyle` into drawable values; a small renderer set (Value, Dual, Bar, Ring, Graph, Glyph) draws them; appearance modes (`monochrome`, `statusTint` default, `categoryColor`) decide color. Split the 3457-line `MenuBarIconRenderer.swift` along those lines.

## Current code
- `iStats/UI/MenuBarIconRenderer.swift` (3457 lines): renders every legacy style.
- `Sources/iStatsCore/MenuBarItemConfig.swift`: `ThroughputLayout`, `MetricDisplayStyle` (+ legacy cases and Codable migration), `supportedStyles`, `PopoverStyle` (removed in 9.2), `defaultConfigs()` (cpu.bar, memory.bar, network.throughput); `MenuBarOrdering.observedOrder(frames:)` (used at `MenuBarController.swift:250`).
- `iStats/App/MenuBarController.swift`: `syncStatusItems`, `startTrackingManualReorder`, `statusItemClicked` (490), `showContextMenu` (519), scrubbing/hover (611+).
- Tests: `MenuBarGeometryInvarianceTests`, `MenuBarDirtyCheckingTests`, `MenuBarItemConfigTests`, renderer tests.
- `PreferencesStore.menuBarAppearance` (9.2), `CategoryPalette`/`CategoryIdentity` (9.1).

## Approach
1. **Core.** `Sources/iStatsCore/WidgetModel.swift`: `enum WidgetStyle { value, dual, bar, ring, graph, glyph }` and `struct WidgetModel` (primary, secondary, fraction 0...1, series, label, status, unavailable). `WidgetModel.make(category:style:reading:history:)` is pure. `MenuBarAppearance` enum (if not already in 9.2) lives here. Map every legacy `MetricDisplayStyle` case to a `WidgetStyle` (+ options) in `WidgetStyle.init(legacy:)`.
2. **Renderers.** Split `MenuBarIconRenderer.swift` into `iStats/UI/MenuBar/` (new group): `WidgetRenderer.swift` (protocol + dispatch), `ValueWidget.swift`, `DualWidget.swift`, `BarWidget.swift`, `RingWidget.swift`, `GraphWidget.swift`, `GlyphWidget.swift`, `WidgetColor.swift` (appearance to `NSColor`). Keep the public renderer entry point so `MenuBarController` call sites do not change in this task.
3. **Geometry rules.** Fixed widths per style (no jitter as digits change; monospaced digits), height 18 pt, template images only in `monochrome`.
4. **Dirty checking.** Cache key = (style, rounded values, appearance, effective appearance); unchanged keys reuse the image (existing behaviour, keep test).
5. **Migration of existing items.** Old `MetricDisplayStyle` values decode through the legacy mapping; no stored data rewritten until the user edits an item.

## Tests
- `WidgetModelTests`: each style from fixtures (fraction clamping, unavailable shows "--", dual primary/secondary, status at thresholds, legacy style mapping total over all legacy cases).
- Geometry invariance: widths constant across value ranges for every style and appearance.
- Dirty checking: unchanged inputs yield the same image object; appearance change invalidates.
- Appearance: `monochrome` produces template images; `statusTint` color follows `StatusLevel`; `categoryColor` uses identity hue.

## Acceptance criteria
- All six styles render for every category that supports them; existing user items render identically or via documented mapping; no width jitter; renderer file split with each file under ~600 lines.

## Risks
- Largest refactor of the phase: land per step (core model, then each renderer) with a green build each time.
- Menu bar item width changes shift neighbouring items: keep widths stable and test.
